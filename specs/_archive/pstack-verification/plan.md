# pstack 검증 관점 도입 Plan

> 작성일: 2026-10-18 / 상태: 완료
> 근거 문서: [spec.md](./spec.md)

## 아키텍처 영향

기존 템플릿·테스트·문서 경계를 사용한다. 외부 의존성, 공개 API, 데이터 스키마, 승인 정책 변경은 없다. 평가 자료는 스타터 유지보수용이며 bootstrap 배포 대상에 넣지 않는다.

## 접근 방식

지정한 Claude Fable 5.1 high의 읽기 전용 리뷰를 받은 뒤 근거가 확인된 최소 개선을 반영한다. pstack 전체 절차를 설치하는 대신 기존 plan과 bootstrap 테스트를 보완한다. 행동 평가 자동화는 모델 비용과 실행 환경 의존성이 있어 수동 사례 준비로 제한한다.

## 단계

- [x] Phase 1: 제안 리뷰와 기존 검증 확인 → 리뷰 근거 확인, 기존 테스트 결과 기록.
- [x] Phase 2: 영향 항목·배포 검증·평가 사례 보완 → 산출물 검사와 의도적 결함 탐지 확인.
- [x] Phase 3: 문서 동기화와 전체 검증 → context와 완료 범위 일치.

## 리스크와 대응

- 소비 프로젝트 템플릿이 무거워짐 → 적용할 때만 쓰는 짧은 항목으로 제한.
- 테스트가 실제 계약을 검증하지 못함 → 격리된 사본에 대표 결함을 넣어 탐지 여부 확인.
- 수동 평가 문서가 실측 성과로 오인됨 → 실행 결과와 설계 검토를 분리하고 미실행 명시.
- 복구: 이번에 추가한 템플릿 항목·테스트·평가 자료만 되돌리면 된다.

## 실행 근거와 승인 상태

- 사용자 요청: 지정 모델로 리뷰하고 개선할 부분을 개선.
- 범위: 앞서 제안한 템플릿, bootstrap 검증, 소규모 행동 평가 사례.
- 권한 정책 변경은 제외하므로 별도 승인 대상 없음. 새로운 중대한 영향이 발견되면 해당 부분만 보류한다.
