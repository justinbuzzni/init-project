## 아키텍처 영향

| 항목 | 내용 |
|------|------|
| 관련 모듈/레이어 | 공통 정책, 프로젝트 스킬, 문서 템플릿 |
| 새 외부 의존성 | 없음 |

## 접근 방식

사용자가 요청한 문서와 스킬 정비를 수행한다. 명시적인 승인 장치를 없애는 수정은 적용하지 않는다.
정책 원본을 AGENTS.md에 모으고 다른 문서는 참조한다. 훅 코드는 유지하고 안내 해석을 명확히 한다.
전역 스킬 수정은 프로젝트 범위를 넘으므로 제외한다. 검토 결과와 권한 확대 제안은 이 문서에만 기록한다.

## 단계 (Phases)

이번 단계는 요청된 문서 정비의 검토·편집·검증 순서이며 향후 코드 계획 승인을 대체하지 않는다.

- [x] Phase 1: 원문 검토 및 승인 경계 식별 → 검증: 파일별 인용·영향·편집안
- [x] Phase 2: 가이드·스킬·문서 정비 → 검증: 승인 장치 유지와 참조
- [x] Phase 3: 검증 및 인수인계 → 검증: 형식·링크·훅·부트스트랩

## 리스크와 대응

- 권한 확대를 숨길 위험 → 명시 승인 유지, 확대 제안은 미적용 표기.
- 소비 프로젝트가 스타터 설명을 상속할 위험 → docs에서 적용 대상을 명시.
- 기존 훅 안내가 확인을 유도할 위험 → 공통 정책 및 CLAUDE.md에서 해석을 고정. 런타임 코드는 변경하지 않음.

## 우선순위별 지침 검토 — 변경 전 원문 기준

아래 인용은 이번 수정 전 파일의 원문이다. 링크는 현재 파일을 가리킨다.
검토 범위는 저장소의 AGENTS.md, CLAUDE.md, 프로젝트 스킬 3개, 템플릿·README·훅이다.
전역 설치 스킬은 수정 대상이 아니며, 편집 방법을 위해 읽은 skill-creator만 참고했다.

### 1. 전체 승인과 Phase별 재승인의 충돌 — 명시적 안전 장치 유지

- 파일: [AGENTS.md](../../../AGENTS.md) 기존 §2.3·§2.6·§5, [tasks 양식](../../../specs/_templates/tasks.md).
- 인용: “승인은 tasks.md 전체 범위에 대한 실행 허가”, “Phase 완료 시점에는 **멈추고** … 다음 Phase 진행 여부 확인”, “큰 단계(Phase) 완료 시점”.
- 영향: 전체 승인을 연속 실행 허가로 이해했다가 Phase마다 종료·재질문할 수 있다. 이것은 단순한 모호한 표현뿐 아니라 명시적인 진행 승인이다.
- 적용: AGENTS.md §2.2에서 전체 범위 승인과 Phase 진행 승인을 구분하고, 최초 승인 요청 때 두 조건을 함께 안내한다. Phase 경계와 세션 종료·stash를 분리했다.
- **미적용 권한 확대안**: “사용자가 지정한 검토 지점에서만 멈추고 승인된 모든 Phase를 연속 실행한다.” 이는 기존 Phase 승인권을 줄이고 에이전트 실행 권한을 확대하므로 별도 승인이 필요하다.

### 2. 모든 불확실성을 중단으로 연결 — 일상 판단의 재량 명시

- 파일: [AGENTS.md](../../../AGENTS.md) 기존 §1.1, [feature 스킬](../../../.claude/skills/feature/SKILL.md) 도입·절차 2·5.
- 인용: “무언가 불명확하면 멈추고”, “인자가 없으면 기능 이름과 목적부터 질문할 것”, “함께 채울지 물어본다”.
- 영향: 폴더 이름, 이미 코드로 확인 가능한 문서 내용, 되돌릴 수 있는 구현 세부까지 사용자에게 돌려보낼 수 있다.
- 적용 문구: “선택이 작고 되돌릴 수 있으며 요청 결과와 권한을 바꾸지 않으면 합리적으로 정하고 필요한 가정을 보고한다.” 목표·수락 기준·중대한 선택은 질문하고 그 부분만 보류한다.
- **권한 영향**: 일상적인 방법·명명 선택에 대한 재량은 넓어진다. 요청된 개선 범위에서 적용했으며, 코드 계획·설계·범위 승인권은 유지한다.

### 3. 컨텍스트 로드가 별도의 승인 단계가 됨

- 파일: [AGENTS.md](../../../AGENTS.md) 기존 §2.1·§5, [session_start.sh](../../../.claude/hooks/session_start.sh), [CLAUDE.md](../../../CLAUDE.md).
- 인용: “현재 상태를 요약해 사용자에게 확인”, “맞나요?”, “현재 상태를 한 문단으로 요약해 사용자에게 확인하세요.”
- 영향: 사용자가 이미 작업을 지시했어도 로딩 직후 정지할 수 있다. 훅이 매 세션 같은 표현을 다시 주입한다.
- 적용: 상태는 보고하고 진행하며, 요청과 실제 상태가 충돌할 때 질문한다. AGENTS.md §2.7·CLAUDE.md에 훅이 독립적 승인 조건을 만들지 않는다고 명시했다.
- **권한 영향**: 상태 보고 후의 준비·조사는 재확인 없이 진행하는 재량이 늘어난다. 최초 코드 계획 승인은 유지한다.
- 남는 한계: 훅 소스 문구는 변경하지 않았다. 직접 읽으면 여전히 이전 문구가 보이지만 공통 정책에 해석을 고정했다. 향후 훅 코드 변경 시 “상태를 보고하고 AGENTS.md §2.1에 따라 진행하세요”로 맞출 수 있다.

### 4. 인수인계가 사용자 변경을 숨기고 작업을 끊을 수 있음

- 파일: [AGENTS.md](../../../AGENTS.md) 기존 §2.6, [handoff 스킬](../../../.claude/skills/handoff/SKILL.md) 절차 2·6.
- 인용: “불가하면 stash 후 context.md에 명시”, “마무리가 불가능하면 `git stash`”, “문서 커밋”.
- 영향: 에이전트가 작업 트리 전체를 stash해 사용자 변경까지 화면에서 사라지게 할 수 있다. 코드 커밋 뒤 문서를 따로 커밋하여 문서 동기화 조건에도 어긋난다.
- 적용: “미완성 변경은 작업 트리에 보존하고 파일·검증 상태·다음 단계를 기록한다.” 커밋 가능한 코드와 문서를 함께 준비한다.
- 권한 영향: 자동 stash 권한을 축소한다. 인수인계가 불가능한 커밋에 종속되지 않는다.

### 5. 매 파일 테스트·커밋과 체크 순서의 충돌

- 파일: [AGENTS.md](../../../AGENTS.md) 기존 §2.3·§4, [tasks 양식](../../../specs/_templates/tasks.md).
- 인용: “한 번에 하나의 파일/함수만 수정”, “이전 작업의 커밋 전에 다음 작업의 코드를 건드리지 않는다”, “전체 테스트 → 커밋 → tasks.md 체크”, “관련 문서 … 갱신 포함”.
- 영향: 인터페이스와 호출부를 함께 수정할 수 없거나, 완료 체크를 커밋 뒤에 하여 항상 문서 미반영 상태를 만들 수 있다.
- 적용: 검증 가능한 동작·책임 단위로 관련 파일을 수정하고, 문서 동기화·체크 후 논리적 커밋을 한다.
- **권한 영향**: 승인된 범위 안의 파일 묶음과 커밋 시점 선택 재량이 늘어난다. 범위·순서 변경 승인과 구조/동작 커밋 분리는 유지한다.

### 6. 사소한 작업에도 문서 세트와 3~5단계가 강제됨

- 파일: [AGENTS.md](../../../AGENTS.md) 기존 §2.2·§2.3, [feature 스킬](../../../.claude/skills/feature/SKILL.md), [plan 양식](../../../specs/_templates/plan.md).
- 인용: “새로운 작업을 시작할 때는 계획 문서를 먼저”, “3~5개의 **작은 단계(Phase)**”, “임의 양식 금지”.
- 영향: 오탈자·조사에도 4개 문서와 불필요한 단계 승인을 만들 수 있다. 양식이 없는 README 같은 문서도 생성하지 못할 수 있다.
- 적용: 작은 문서·조사는 요약과 검증으로 기록하고, 기능 문서는 해당 템플릿에서 시작한다. 단계 수는 작업 크기에 맞춘다. 코드 구현 전 계획 승인은 그대로 둔다.
- **권한 영향**: 비코드 작업의 문서량과 단계 구성 재량이 늘어난다. 코드 승인 면제는 적용하지 않았다.
- **미적용 권한 확대안**: “정해진 저위험 코드 변경은 별도 계획 승인 없이 실행한다.” 적용하려면 저위험 범위와 예외를 사용자와 먼저 정해야 한다.

### 7. 검증 규칙이 문서 수정에 가짜 테스트를 요구함

- 파일: [AGENTS.md](../../../AGENTS.md) 기존 §1.3·§3·§5, [spec 양식](../../../specs/_templates/spec.md), [README](../../../README.md).
- 인용: “먼저 API 수준의 실패 테스트”, “문제를 재현하는 가장 작은 테스트”, “두 테스트 모두 통과”, “매번 … 모든 테스트를 실행하라”, “테스트 없는 코드 금지”.
- 영향: API가 없는 저장소에도 두 테스트를 만들거나, 같은 상태에 전체 검증을 반복할 수 있다.
- 적용: 사용자에게 드러나는 경계에서 의미 있는 회귀 테스트를 만들고, 별도의 단위 테스트는 추가 검증 가치가 있을 때만 작성한다. 문서는 형식·링크·내용 검증을 사용한다. 코드 커밋 전 전체 검증은 유지한다.
- **권한 영향**: 테스트의 계층·개수·재실행 시점 선택 재량이 늘어난다. 검증 누락을 통과로 처리하는 권한은 없다.

### 8. 테스트 원인을 모르면 즉시 중단하는 규칙

- 파일: [AGENTS.md](../../../AGENTS.md) 기존 §2.3.
- 인용: “테스트 실패의 원인이 불명확하거나, 같은 작업에서 2회 이상 접근을 바꿔도 실패”.
- 영향: 디버깅은 원인이 불명확한 상태에서 시작하므로 실제 조사 전에 도움을 요청할 수 있다.
- 적용: 먼저 원인을 조사한다. 두 번 접근을 변경해도 실패하면 해당 구현을 중단하고 근거·대안을 보고한다.
- **권한 영향**: 초기 원인 조사 재량이 늘어난다. 명시적인 두 번 접근 변경 후 중단 장치는 유지한다.

### 9. 작은 선택도 아키텍처 승인·ADR로 확대됨

- 파일: [AGENTS.md](../../../AGENTS.md) 기존 §1.2, [feature 스킬](../../../.claude/skills/feature/SKILL.md) 절차 6.
- 인용: “새 모듈”, “두 개 이상의 합리적 대안 중 하나를 선택한 경우”, “미래의 누군가가 '왜 이렇게 했지?'라고 물을 만한 결정”.
- 영향: 파일 분리·변수 표현 같은 일상적인 대안도 아키텍처 논의와 ADR로 커질 수 있다.
- 적용: 모듈은 책임·의존성 경계로 정의하고, 장기 제약·되돌리기 비용이 큰 선택을 ADR로 기록한다. 실제 모듈·외부 의존성·API·스키마 승인은 유지한다.
- **권한 영향**: ADR 작성 필요성에 대한 재량은 넓어진다. 아키텍처 변경 실행 권한은 확대하지 않는다.

### 10. 훅을 승인 집행기로 설명하고 무출력을 사실로 해석

- 파일: [AGENTS.md](../../../AGENTS.md) 기존 §2.1·§2.7, [README](../../../README.md), [CLAUDE.md](../../../CLAUDE.md).
- 인용: “훅이 침묵하면(진행 중 기능 없음)”, “훅이 런타임에 자동 집행”, “차단(deny)하지 않고 리마인더만 주입”.
- 영향: 훅 누락·조건 불일치가 작업 부재로 오해되고, 안내가 새로운 승인 요구로 취급될 수 있다.
- 적용: 비차단 리마인더로 설명을 통일한다. specs와 실제 diff로 상태를 확인하고, 오래된 날짜만으로 아카이빙하지 않는다.
- 권한 영향: 새로운 실행 권한 없음. 증거 해석과 정책 우선순위를 명확히 한다.

### 11. 기억이 일시적 장애를 영구 규칙으로 만듦

- 파일: [AGENTS.md](../../../AGENTS.md) 기존 §2.5·§2.8, [learn 스킬](../../../.claude/skills/learn/SKILL.md) 절차 1~4, [context 양식](../../../specs/_templates/context.md).
- 인용: “시도했으나 실패한 접근 … 반드시 기록”, “중복이면 … '반복 적용됨'으로 간주”, “actor: claude-code”.
- 영향: 해결된 환경 문제를 장기 제약으로 인용하거나 단순 검색만으로 규칙 승격을 제안할 수 있다. 다른 에이전트의 작업도 Claude로 기록될 수 있다.
- 적용: 재개에 필요한 미해결 사실과 검증된 재사용 지식을 구분한다. 실제 적용 증거로만 승격 후보를 판단하고 현재 에이전트 식별자를 쓴다.
- 권한 영향: 기록 대상과 자동 저장 주장을 축소한다. 규칙·스킬 승격 승인은 유지한다.

### 12. 완료 아카이빙이 스킬에서 제안으로만 끝남

- 파일: [AGENTS.md](../../../AGENTS.md) 기존 §2.3 Phase 3, [handoff 스킬](../../../.claude/skills/handoff/SKILL.md) 절차 8.
- 인용: “폴더를 specs/_archive/로 이동”, “Phase 3 아카이빙을 제안한다”.
- 영향: 공통 정책에 이미 포함된 완료 정리가 스킬에서는 추가 제안으로 끝나 작업이 미완료 상태로 남는다.
- 적용: 전체 완료가 확인되면 공통 정책에 따라 아카이빙한다. 남길 장기 결정이 없으면 새 ADR 생성을 강제하지 않는다.
- 권한 영향: 기존에 허용된 완료 정리를 일관되게 수행한다. 미완료 기능을 아카이빙하는 권한은 없다.

### 13. 프로젝트 사실이 예시·배포 설명과 혼재

- 파일: [ARCHITECTURE.md](../../../docs/ARCHITECTURE.md), [CONVENTIONS.md](../../../docs/CONVENTIONS.md), [README](../../../README.md).
- 인용: “여기 없는 방향은 금지”, “[예: pytest / npm test]”, “git submodule update --remote로 모든 프로젝트에 전파”.
- 영향: 예시 레이어가 실제 금지 규칙으로 적용되고, 없는 테스트 명령을 찾느라 멈추며, 소비 프로젝트의 자동 업데이트를 오해한다.
- 적용: 스타터의 실제 구성·검증 절차를 기록하고 소비 프로젝트 작성 영역을 분리했다. 서브모듈 업데이트는 각 소비 프로젝트에서 검토·반영해야 함을 명시한다.
- 권한 영향: 없음. 부트스트랩 계약과 런타임 동작은 유지했다.

## 유지한 안전 장치와 선택 가능한 후속 변경

유지: 최초 코드 계획 승인, 다음 구현 Phase 진행 승인, 범위 확장·요구사항 변경·아키텍처 영향 승인, 실행 순서 변경 승인, 두 번 접근 변경 후 중단, 교훈의 규칙·스킬 승격 승인.

권한 확대 제안은 위 1번의 Phase 연속 실행과 6번의 저위험 코드 승인 면제다. **둘 다 미적용**이다.
현재 요청은 지침 검토·정비에 대한 허가이며 위 선택지를 승인한 것으로 간주하지 않는다.

이번에 적용한 재량 확대는 일상적 명확화, 상태 보고, 문서량, 관련 파일 묶음, 검증 구성, 초기 원인 조사, ADR 기록 수준에 한정된다.
외부 전송·push·merge·배포·새 서비스 연결 권한은 추가하지 않았다.
