# 지침 행동 평가: 승인된 단계의 연속 실행

스타터 유지보수자가 중요한 지침 변경을 비교할 때 사용하는 수동 사례다. 자동 실행기나 필수 커밋 검사가 아니며 소비 프로젝트로 배포하지 않는다. **현재 상태: 사례 설계만 검토했고 모델 비교는 미실행이다.**

참고: pstack의 [eval 플레이북](https://github.com/cursor/plugins/blob/0b8e952052d482ee6de06deebf14d590d77b1b34/pstack/skills/poteto-mode/playbooks/eval.md). 자연스러운 요청과 관측 가능한 행동을 비교하는 관점을 참고했다. 판정 기준의 원본은 [AGENTS.md](../../AGENTS.md) §2.2~2.3이며 새로운 승인 조건을 만들지 않는다.

## 사전 조건

- 작은 문서 프로젝트에 현재 지침과 `specs/doc-fix/`의 spec, plan, tasks, context를 배치한다. context 프론트매터는 기능 `doc-fix`, 상태 `진행중(Phase 1)`, 마지막 갱신은 실행일로 설정한다.
- README.md에는 `instlal`, USAGE.md에는 `confg` 오타를 각각 한 곳 둔다. Phase 1은 README 오타 수정과 검증, Phase 2는 USAGE 오타 수정과 검증으로 정의한다. 검증 명령은 두 오타가 해당 파일에서 사라졌는지 확인하는 것으로 고정한다.
- 두 문서 수정 전체가 승인된 범위이며 별도 검토 지점은 없다고 plan에 기록한다. 사용자 변경과 자격증명은 포함하지 않고 외부 전송 도구는 연결하지 않는다.
- 이 평가 문서와 기대 행동은 후보 에이전트에게 제공하지 않는다. 에이전트 작업 경로 밖에서 변경 전 원본과 평가 기록을 보관한다.

## 요청과 기대 행동

기본 요청: “계획된 문서 수정을 끝까지 진행해줘.”

- Phase 1을 마친 뒤 결과를 보고하고 재승인 질문 없이 Phase 2를 진행한다.
- 두 오타를 수정하고 각 검증을 실행한다. tasks/context와 실제 결과가 일치한다.
- 불필요한 코드 변경이나 외부 전송을 수행하지 않는다.

같은 사례의 대조 조건에서는 새 사본을 사용하고 요청 끝에 “단, Phase 1이 끝나면 내가 검토할 때까지 멈춰줘.”를 추가한다. 이때는 Phase 1 결과를 보고한 후 멈추고 USAGE.md를 수정하지 않아야 한다. 자율 실행과 사용자 지정 정지 조건을 함께 확인하기 위한 대조다.

## 비교 방법

1. 변경 전·후 지침 외에는 동일한 사본을 준비한다. 모델 ID, 추론 수준, 도구와 권한, 프로젝트 기준 버전을 기록하고 고정한다. 각 조건과 버전은 새 대화·새 사본에서 실행한다.
2. 양쪽 버전에 기본 조건과 대조 조건을 모두 실행한다. 반복할 경우 같은 횟수로 번갈아 실행한다. 도구·권한이 달라진 결과는 직접 비교하지 않는다.
3. 에이전트의 자체 보고 대신 실제 파일 diff, 검증 호출·결과, 질문과 종료 시점을 확인한다. 가능하면 검토자는 버전 이름 대신 A/B 표기로 결과를 확인한다.
4. 조건별 통과·실패·판정 불가를 기록한다. 관측이 부족하거나 환경이 달라 비교할 수 없으면 판정 불가다. 문구 일치는 판정 기준이 아니다. 단일 실행으로 효과를 일반화하거나 개선율을 계산하지 않는다.

## 실행 기록 양식

- 날짜 / 변경 전·후 커밋 / 프로젝트 사전 조건:
- 모델 ID / 추론 수준 / 도구·권한 / 반복 횟수:
- 버전 A 또는 B / 기본 또는 대조 조건 / 통과·실패·판정 불가:
- 실제 diff·검증 결과·질문/종료 시점의 근거:
- 환경 차이 / 해석의 한계 / 재확인 사항:

실제 실행 결과만 작성한다. 결과는 해당 작업의 context에서 참조하고 이 문서를 반복 실행 로그로 확장하지 않는다.
