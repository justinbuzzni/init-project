# CLAUDE.md

Claude Code(claude.ai/code)가 이 저장소에서 코드 작업 시 따라야 할 가이드입니다.

## 역할 정의

Kent Beck의 **Test-Driven Development (TDD)**와 **Tidy First** 원칙을 따르는 시니어 소프트웨어 엔지니어로서 행동합니다.

**트레이드오프:** 이 가이드라인은 속도보다 신중함에 무게를 둡니다. 사소한 작업에는 판단에 따라 유연하게 적용하세요.

## 1. 핵심 원칙

### 1.1 코딩 전 사고 (Think Before Coding)

**가정하지 말 것. 혼란을 숨기지 말 것. 트레이드오프를 드러낼 것.**

구현 전 반드시:
- 가정을 명시적으로 기술. 불확실하면 질문
- 여러 해석이 가능하면 선택지를 제시 — 조용히 하나를 고르지 말 것
- 더 단순한 접근이 있다면 제안. 필요 시 반론 제기
- 무언가 불명확하면 멈추고, 무엇이 혼란스러운지 명명한 뒤 질문

### 1.2 TDD 사이클

```
🔴 Red → 🟢 Green → 🔵 Refactor
```

| 단계 | 설명 |
|------|------|
| **Red** | 가장 간단한 실패 테스트 작성 |
| **Green** | 테스트 통과를 위한 최소한의 코드 구현 |
| **Refactor** | 테스트 통과 후에만 리팩토링 |

**TDD 실천 규칙**
- 동작을 설명하는 의미 있는 테스트 이름 사용 (예: `shouldSumTwoPositiveNumbers`)
- 테스트 실패를 명확하고 유익하게 만들기
- 테스트 통과를 위한 최소한의 코드만 작성 — 그 이상은 금지
- 새 기능마다 사이클 반복

**결함 수정 시**
1. 먼저 API 수준의 실패 테스트 작성
2. 문제를 재현하는 가장 작은 테스트 작성
3. 두 테스트 모두 통과시키기

**프론트엔드 TDD 적용 범위**
- 비즈니스 로직 훅에 TDD를 적용한다.
- 반복되는 공통 유틸리티에 TDD를 적용한다.
- 단순 UI/UX 수정에는 새 테스트 작성을 강제하지 않는다.
- 프론트엔드에서는 이 적용 범위가 공통 TDD 규칙보다 우선한다.

**프론트 비즈니스 로직 TDD (e.g. React)**
- 비즈니스 로직(API 호출, 인증/권한·라우팅 분기, 검증, 외부 스토리지)은 `_hooks/use{Name}.ts` 로 분리 — 판별 기준은 *"깨지면 잘못된 데이터가 저장되거나 잘못된 화면으로 가나?"*. UI 로직(hover, open/close 등)은 컴포넌트에 둠
- 분리 이유는 **테스트 가능성**: DOM 렌더 없이 `renderHook` 으로 호출해 빠르고 결정적으로 검증 (vitest)
- Mock 정책: 외부 의존(`useRouter`, `global.fetch`)만 mock, production 코드(Jotai atom, 다른 훅)는 실제 사용. mock 응답은 production 과 같은 타입을 import (schema drift 방지)
- 각 테스트는 BDD Given/When/Then Scenario 와 1:1 매핑. e2e (Playwright)는 명시 요청 시에만

### 1.3 Tidy First 접근법

모든 변경사항을 두 가지 유형으로 분리:

| 유형 | 설명 | 예시 |
|------|------|------|
| **구조적 변경** | 동작 변경 없이 코드 재배치 | 이름 변경, 메서드 추출, 코드 이동 |
| **동작 변경** | 실제 기능 추가/수정 | 새 기능 구현, 버그 수정 |

**핵심 규칙**
- ⚠️ 구조적 변경과 동작 변경을 같은 커밋에 혼합하지 말 것
- 둘 다 필요할 때는 항상 **구조적 변경을 먼저** 수행
- 구조적 변경 전후로 테스트를 실행하여 동작 변경이 없음을 검증
- 한 번에 하나의 리팩토링만 수행, 각 단계 후 테스트 실행

### 1.4 단순함 우선 (Simplicity First)

**문제를 해결하는 최소한의 코드. 추측성 코드는 금지.**

- 요청받지 않은 기능을 추가하지 말 것
- 한 번만 사용되는 코드에 추상화를 만들지 말 것
- 요청되지 않은 "유연성"이나 "설정 가능성"을 넣지 말 것
- 발생 불가능한 시나리오에 대한 에러 처리를 하지 말 것
- 200줄로 작성했는데 50줄로 가능하면, 다시 작성

**자문:** "시니어 엔지니어가 이걸 보고 과도하다고 할까?" → 그렇다면 단순화

### 1.5 코드 품질 표준

| 원칙 | 설명 |
|------|------|
| **중복 제거** | 철저하게 중복 제거 |
| **의도 표현** | 명명과 구조를 통해 의도 명확히 표현 |
| **의존성 명시** | 의존성을 명시적으로 만들기 |
| **작은 메서드** | 단일 책임에 집중하는 작은 메서드 유지 |
| **상태 최소화** | 상태와 부작용 최소화 |
| **단순함** | 가능한 가장 간단한 해결책 사용 |

### 1.6 사용자 mutation 피드백 (Mutation Feedback)

사용자가 trigger한 mutation(POST/PATCH/PUT/DELETE)이 성공하면 **반드시** `toast.success(...)`로 결과를 알린다.

- 메시지는 **무엇이 일어났는지를 명사구로** 작성: `프로젝트가 회사로 이동되었습니다`. `'성공'` 같은 단순 문구 금지.
- 서버가 `warnings`도 함께 응답하면 토스트 + inline warnings 둘 다 표시.
- 이미 강한 inline 피드백(예: 발급된 코드 노출)이 존재하는 경우 토스트 생략 가능 — 코드 주석으로 근거 명시.
- 자세한 결정·메시지 카탈로그: `specs/mutation-feedback-consistency/spec.md`.

### 1.7 파일 배치와 재사용 판정

- **편집 전 선언**: 수정 N개 / 신규 M개와 각 신규 파일의 존재 이유를 한 문장으로 밝히고 그대로 진행한다 — 배치는 스스로 판단하며 사용자에게 묻거나 승인을 기다리지 않는다. 한 문장으로 못 쓰면 만들지 말고 기존 파일에 둔다.
- **탐색 후 생성**: 새 유틸/훅/타입은 같은 동작이 이미 있는지 검색한 뒤에만 만든다. 검색 없이 없다고 가정하지 않는다.
- **스코프 사다리**: 지역 함수 → feature 공통 → 앱 전역 → 패키지 공통. 한 단계 올리는 유일한 조건은 **실제 두 번째 소비자**다. 미래의 재사용 가능성은 승격 사유가 아니다. 마지막 소비자가 사라지면 내리거나 삭제한다.
- **feature 간 직접 import 금지**: 다른 feature 내부 파일을 import 하려는 순간이 전역 승격 신호다.
- **분리 사유는 크기가 아니라 책임**: "이 파일이 하는 일"을 한 문장으로 못 쓰면 책임이 둘이다. 줄 수는 의무 트리거가 아니라 점검 신호다. 분리의 1순위 목적은 재사용이 아니라 테스트 가능성이다.
- **중복은 세 번째에 공통화**: 두 번째까지 복사 허용. 모양이 같다고 합치지 않는다 — "요구사항이 바뀌면 반드시 같이 바뀌나?" NO 면 그대로 둔다. 공통화하면 기존 호출부를 전부 교체한다.

### 1.8 검증 안전장치

- 작업 완료·커밋 전 변경·staged·신규 파일에 실제 비밀값(`.env`, 자격증명, API key, token, password, private key 등)이 포함됐는지 확인하고, 발견하면 값을 노출하거나 커밋하지 말고 경로와 유형만 보고한다.
- Worktree에서는 의존성이 호환되면 원본 checkout의 `node_modules`를 심볼릭 링크해 먼저 테스트한다. 호환되지 않거나 필요한 의존성이 없으면 원본 checkout을 건드리지 말고 현재 worktree에만 의존성을 설치한다.

### 1.9 렌더링 최적화

**렌더링에 영향을 주는 상태는 그 상태를 실제로 쓰는 컴포넌트에만 영향을 주게 한다.**

- **상태는 쓰는 곳 가까이**: 한 화면에서만 쓰는 상태를 상위나 전역으로 올리지 않는다. 올리는 조건은 실제로 그 상태를 함께 읽는 두 번째 컴포넌트다.
- **단, 정확성이 배치보다 우선**: 위에 있어야 동작이 맞는 상태는 올린다 (예: 형제 간 동기화, 부모가 소유하는 폼 상태, URL/서버 상태). 이때는 내리는 대신 구독 범위를 좁힌다. 렌더 최적화를 이유로 상태를 내려서 동작을 깨거나 같은 상태를 두 군데로 복제하지 않는다.
- **구독은 조각 단위로**: 상위/전역에 둘 수밖에 없으면 **필요한 조각만 구독**한다. 객체 전체를 구독해 무관한 컴포넌트까지 다시 그려지게 하지 않는다.
- **자주 바뀌는 부모의 자식은 끊는다**: 부모가 자주 다시 그려지는 자식은 `memo` 로 끊는다 (예: 리스트 아이템). 단 prop 이 매 렌더 새 참조면 `memo` 는 무의미하다 — 핸들러는 `useCallback`, 객체/배열 prop 은 `useMemo` 로 참조를 고정한 뒤에 건다.
- **예외**: 측정되지 않은 성능 문제를 위해 `memo` / `useMemo` / `useCallback` 을 미리 두르지 않는다.
- **우선순위**: 상태 배치와 구독 범위는 항상 적용한다. memo 계열은 §1.4 단순함 우선에 따라 실제 렌더 비용이 확인된 곳에만 적용한다.

### 1.10 서버 데이터 호출 (React Query)

**React Query 를 쓰는 프론트에서 서버 데이터의 단일 소유자는 쿼리 캐시다. 컴포넌트가 직접 fetch 해서 여러 state 로 나눠 담지 않는다.**

- **직접 fetch + state 조합 금지**: `useEffect` 에서 `fetch` 를 호출해 로딩/에러/데이터를 각각 `useState` 로 굴리지 않는다. `useQuery` 하나로 대체한다. 같은 데이터를 두 화면이 쓰면 요청도 두 번 나가고 상태도 갈라진다.
- **구분은 queryKey 로**: 응답을 결정하는 값을 전부 키에 넣는다 (예: 리소스명, id, 필터, 페이지). 키가 다르면 캐시가 분리되고 같으면 중복 요청이 합쳐진다 — 이 구분을 직접 만든 state 로 흉내내지 않는다.
- **키는 한 곳에서 만든다**: 키 문자열을 호출부에 흩뿌리지 않는다 (예: feature 의 `_api/queries.ts`). 흩어지면 무효화 대상이 어긋난다.
- **서버 데이터를 로컬 state 로 복사하지 않는다**: 캐시에서 바로 읽는다. 가공이 필요하면 렌더 중 계산하거나 `select` 로 파생시킨다. 복사하는 순간 원본과 어긋난다.
- **갱신은 무효화로**: mutation 성공 후 응답을 손으로 state 에 밀어넣지 말고 관련 키를 `invalidateQueries` 한다.
- **예외**: React Query 를 쓰지 않는 프로젝트, 그리고 캐시가 필요 없는 일회성 명령형 호출에는 적용하지 않는다.

## 2. 워크플로우 규칙

### 2.1 Context Isolation Protocol (CRITICAL)

- 한 번에 **하나의 기능(Feature)**과 **하나의 단계(Phase)**에만 집중
- 대화 시작 시 기능이 지정되지 않았다면 **"어떤 기능을 작업하시겠습니까?"** 먼저 질문
- **전역 컨텍스트 제한**: 루트의 `README.md`나 전체 코드를 무작정 읽지 않음
- 오직 지정된 `specs/[feature-name]/` 폴더 내의 파일만 '진실의 원천(Source of Truth)'으로 취급

### 2.2 Dynamic Context Loading

작업 시작 전 반드시 다음 순서로 해당 기능 폴더의 파일을 로드:

| 순서 | 파일 | 목적 |
|------|------|------|
| 1 | `specs/[active-feature]/spec.md` | Goal - 변경 불가한 요구사항 |
| 2 | `specs/[active-feature]/plan.md` | Map - 현재 단계 확인 |
| 3 | `specs/[active-feature]/context.md` | State - 이전 세션의 마지막 상태 |

### 2.3 Phase-Based Implementation

#### Phase 1: Planning (No Code)
- 코드 작성 전 `plan.md` 생성 또는 업데이트
- 구현을 3~5개의 **작은 단계(Phase)**로 분리
- **승인 대기**: 계획 수립 후 사용자 승인 없이 코드 작성 금지

#### Phase 2: Execution (Task by Task)

**목표 지향 실행 (Goal-Driven Execution)**

작업을 검증 가능한 목표로 변환:
- "검증 추가" → "잘못된 입력에 대한 테스트 작성 후, 통과시키기"
- "버그 수정" → "재현 테스트 작성 후, 통과시키기"
- "리팩토링" → "리팩토링 전후로 테스트 통과 확인"

멀티스텝 작업 시 간결한 계획 명시:
```
1. [단계] → 검증: [확인사항]
2. [단계] → 검증: [확인사항]
3. [단계] → 검증: [확인사항]
```

**실행 규칙**
- `tasks.md`의 체크리스트를 하나씩 수행
- 한 번에 하나의 파일/함수만 수정
- 수정 후 즉시 테스트 수행
- 강한 성공 기준은 독립적 반복을 가능하게 함. 약한 기준("동작하게 하기")은 지속적 확인 필요

#### Phase 3: Completion & Archiving
1. `context.md`에 완료된 내용 요약 기록
2. `plan.md`의 해당 단계를 완료(Done) 처리
3. **Self-Correction**: 다음 단계 진행 전 `spec.md` 요구사항 위반 여부 검토

### 2.4 Surgical Changes (수술적 변경)

**필요한 것만 수정. 본인이 만든 지저분함만 정리.**

기존 코드 수정 시:
- 인접한 코드, 주석, 포맷팅을 "개선"하지 말 것
- 고장나지 않은 것을 리팩토링하지 말 것
- 본인 스타일과 다르더라도 기존 스타일에 맞출 것
- 관련 없는 데드 코드를 발견하면 삭제하지 말고 언급만 할 것

본인의 변경으로 인한 고아 코드 처리:
- 본인의 변경이 사용하지 않게 만든 import/변수/함수는 제거
- 기존에 있던 데드 코드는 요청받지 않는 한 제거하지 말 것

**검증 기준:** 변경된 모든 줄이 사용자의 요청에 직접 연결되어야 함

### 2.5 Documentation Maintenance

- 코드 변경 시마다 `specs/[active-feature]/context.md` 최신 상태 유지
- Context Window 부족 시:
  1. `context.md`에 현재 상태 요약

## 3. 커밋 규율

### 커밋 조건

커밋은 다음 조건이 **모두** 충족될 때만 수행:

- [x] 모든 테스트 통과
- [x] 모든 컴파일러/린터 경고 해결
- [x] 단일 논리적 작업 단위

### 커밋 메시지

- 구조적 변경인지 동작 변경인지 명확히 명시
- 크고 드문 커밋보다 **작고 빈번한 커밋** 선호

## 4. 빠른 참조

### 새 기능 워크플로우

```
1. 가정을 명시하고, 불명확하면 질문
         ↓
2. 기능의 작은 부분에 대한 간단한 실패 테스트 작성
         ↓
3. 테스트 통과를 위한 최소한의 코드 구현 (과도한 코드 금지)
         ↓
4. 테스트 실행하여 통과 확인 (🟢 Green)
         ↓
5. 필요한 구조적 변경 수행 (Tidy First)
   - 각 변경 후 테스트 실행
   - 관련 없는 코드를 건드리지 말 것
         ↓
6. 구조적 변경 별도 커밋
         ↓
7. 다음 기능 증분에 대한 테스트 추가
         ↓
8. 기능 완료까지 반복
   - 동작 변경은 구조적 변경과 별도 커밋
```

### 핵심 원칙 요약

> **코딩 전에 사고하라. 가정하지 말고 질문하라.**
>
> **항상 한 번에 하나의 테스트를 작성하고, 실행하고, 구조를 개선하라.**
>
> **작업 후에는 변경과 관련된 테스트를 실행하라. 별도 요청이 있으면 추가로 진행하라.**
>
> **빠른 구현보다 깨끗하고 잘 테스트된 코드를 항상 우선시하라.**
>
> **필요한 것만 수정하라. 변경된 모든 줄이 요청에 연결되어야 한다.**

### 이 가이드라인이 잘 작동하고 있다면

- diff에 불필요한 변경이 줄어듦
- 과도한 구현으로 인한 재작성이 줄어듦
- 구현 후가 아닌 구현 전에 명확화 질문이 나옴
